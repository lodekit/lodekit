# Docs Content v1 — Design

**Date:** 2026-07-12
**Status:** Approved (recommendations accepted in absentia — person AFK, autonomous session)

## 1. Goal

Fill the Starlight scaffold (`web/docs`, `@lodekit/web-docs`) with the first real
documentation: full coverage from a non-engineer "what is Lodekit" through service
fundamentals to a complete SDK API reference with examples. This is the "docs content
and IA" item parked on the roadmap by the docs-site v1 slice
(`docs/specs/2026-07-06-docs-site-v1-design.md` §4).

Benchmarks: **Obsidian Help** (friendly, task-oriented, basics-first progression) for
the person-facing half; **Raycast developer docs** (clean guides-vs-reference split,
progressive complexity, code in every reference page) for the builder-facing half.

## 2. Audiences and the reading line

One site, one sidebar, three readers — ordered so each reader stops where their needs
end:

1. **The person (non-engineer)** — installs Lodekit, talks to their agent, uses the
   dashboard. Served by *Start here* and *Using Lodekit*. No code required to follow.
2. **The curious person / builder-adjacent** — wants to understand what the services
   are and when to use which. Served by *Services*: each page teaches the underlying
   systems concept (why an event bus, at-least-once delivery, telemetry vs events)
   before Lodekit's take on it.
3. **The engineer (or the person reading over their agent's shoulder)** — wants the
   stack, the app contract, and exact signatures. Served by *Building apps*, *SDK
   reference*, and *Reference*.

Docs are human-facing; the Skill remains the agent-facing instruction pack
(`context.md` — "Docs vs Skill"). Content may overlap; the audiences never do.

## 3. Information architecture

Six sidebar groups, explicit (not autogenerated) in `astro.config.mjs`. 38 pages
total including the splash.

```
(splash) index.mdx — hero, three entry doors (Start here / Services / SDK reference)

Start here/                        # non-engineer friendly
  what-is-lodekit                  # positioning, what you can build, agent-driven model
  how-lodekit-works                # mental model + big-picture DIAGRAM (manager, runtime,
                                   #   dashboard, agent, apps); build lifecycle
  install                          # get Lodekit.app, first run, what appears on disk
  connect-your-agent               # MCP registration + skill, verbatim snippets
  your-first-app                   # walkthrough: ask agent → watch build → open app

Using Lodekit/                     # the person's manual (Obsidian-style)
  dashboard                        # tour of every view; stubs marked "coming soon"
  your-lodekit-folder              # root, apps/, data/, backup story + storage-tiers DIAGRAM
  manager                          # menubar states, Launch at Login, start/stop/restart
  theming                          # theme.css token overrides (global + per-app)

Services/                          # fundamentals teaching (the explicit ask)
  overview                         # the catalog; four-way storage boundary + decision DIAGRAM
  database                         # relational modeling, schema migration, why destructive
                                   #   changes are gated (expand-copy)
  kv                               # app memory, TTLs, atomic counters, KV-vs-DB rule
  files                            # blob storage, S3 semantics (slug identity, put-replaces),
                                   #   index-vs-bytes split, Finder-browsable
  events                           # pub/sub, append-only logs, offsets & replay, "events are
                                   #   not the system of record" + event-flow DIAGRAM
  tasks                            # queues vs schedules, at-least-once + idempotency, retries
                                   #   & backoff, catch-up + run-lifecycle DIAGRAM
  logs                             # telemetry vs events, levels, structured fields, retention
  settings                         # person-writes/app-reads, declared schema, effective values
  secrets                          # encryption at rest, server-only reads, link-as-grant,
                                   #   why browser/agent never see values

Building apps/                     # developer guides (Raycast-Basics-style)
  the-stack                        # TanStack Start + React + TS + Tailwind; shared toolchain;
                                   #   "bundled for apps, buildless for you"
  app-anatomy                      # the app contract: manifest, src/routes, router,
                                   #   declaration files; annotated folder tree
  data-and-server-functions        # loaders, createServerFn, trust-boundary validation
  live-updates                     # events.watch → router.invalidate pattern, SSE model
  using-the-ui-library             # @lodekit/ui imports, theme.css, component list pointer

SDK reference/                     # one page per handle (Raycast-API-style)
  overview                         # import model, isomorphism matrix (client/server/both),
                                   #   error semantics, TTL-in-seconds convention, appId
  kv                               # every method: signature, params, returns, example
  db                               # createDb, src/db.ts contract, push rules, query examples
  files                            # put/get/url/stat/delete/list/copy/move + FileStat
  events                           # emit/watch/list + LodekitEvent + limits
  tasks                            # task() config + enqueue/cancel/runs/list + TaskRun/TaskInfo
  settings                         # defineSettings + field builders + get/all/watch
  secrets                          # defineSecrets/secret + get + SecretUnavailableError
  logs                             # debug/info/warn/error + console capture

  file-locations                   # what lives where on disk; backup guidance

  glossary                         # person-facing subset of context.md vocabulary
```

Rationale for the Services/SDK split: the person's ask — "explain each service in a
high level … almost as you are teaching the user fundamentals of building reliable
distributed systems" — needs room that would crush a reference page, and reference
readers scanning for a signature don't want essays. Every Services page ends with a
"the API" pointer to its SDK page; every SDK page opens with a one-liner pointing back
at the concept page.

## 4. Content sources and the honesty policy

- **Ground truth is shipped code on `master`** (the `docs` branch's base). Three
  exploration reports (SDK surface, platform facts, showcase samples) captured the
  exact signatures, defaults, limits, and behaviors; the spec's companion facts pack
  seeds every writer.
- **Code samples come from the Greenhouse showcase app** (`root/apps/greenhouse`) —
  real, shipped, DoD-covered code, lightly trimmed — plus the Welcome app's kv
  counter. Invented samples only where Greenhouse has no coverage yet
  (`defineSettings`, `defineSecrets`, `events.emit`), and those must match the SDK
  signatures exactly.
- **Document only what ships.** The dashboard's Data, Tasks, and Themes views are
  stubs → the dashboard page says "coming soon" for exactly those three. Gateways
  (unfolded branch) get zero mention. Install is honest about the assisted alpha:
  ad-hoc signed, right-click → Open, arm64-only, artifact handed to you (no public
  download yet).
- **Terminology is `context.md`'s, verbatim** — app (not tool), scaffold, service
  names (kv-store/db-store/…), Lodekit root, backup tree, person-facing "Engine" only
  when describing that dashboard section.

## 5. Service pages — the teaching structure

Each Services page follows one shape (the "fundamentals" frame the person asked for):

1. **The idea** — the general systems concept, tool-agnostic (2–4 paragraphs): what
   problem this class of service solves and the classic trade-offs (durability vs
   disposability, telemetry vs business events, at-least-once and why idempotency
   matters, blob-store identity semantics).
2. **When to use it** — decision rules, including the cross-service boundaries
   (Database vs KV vs Settings vs Secrets; Events vs Logs), with a short
   "use it for / don't use it for" list.
3. **How it works in Lodekit** — the concrete design: where data lives, what the
   dashboard shows, what happens on failure, one real code sample.
4. **Limits** — a small table (retention, caps, defaults) consistent with the
   limits-and-retention reference page.
5. **API** — pointer to the SDK page.

## 6. Diagrams

Hand-authored inline SVG as small Astro components in `web/docs/src/components/`,
imported from MDX. Colors bind to Starlight theme variables (`--sl-color-*`) so both
color schemes work; no mermaid dependency (build-time mermaid needs a headless
browser; client-side mermaid fights theming and adds a runtime dep).

Six diagrams:

| Diagram | Page | Shows |
|---|---|---|
| Big picture | how-lodekit-works | person + agent → manager → runtime (apps, services, dashboard, MCP) |
| Build lifecycle | how-lodekit-works | save → watcher → build → ready (worker swap), SSE to dashboard |
| Storage tiers | your-lodekit-folder | backup tree vs State vs Cache, cost-of-loss framing |
| Storage decision | services/overview | db vs kv vs settings vs secrets vs files flowchart |
| Event flow | services/events | emit → append-only log → live SSE fan-out + `list` replay from offset |
| Task run lifecycle | services/tasks | queued → running → succeeded/failed/canceled, retry backoff loop |

## 7. Theming (light touch)

One `src/styles/custom.css` registered via Starlight's `customCss`:

- Accent scale from cork amber (`#CE6F26` light / `#E08A3C` dark, links
  `#9C4D10`/`#F6AD64`) per `design.md`.
- Fonts: Fraunces for headings, Hanken Grotesk for body/UI, via Google Fonts import
  (same as the landing site today; self-hosting is a parked roadmap item for
  `packages/ui`, not this slice).
- Nothing else — no component overrides, no shared design layer with the landing site
  (that stays parked on the roadmap).

## 8. Site chrome

- `astro.config.mjs`: explicit sidebar (six groups above), `title: "Lodekit"`,
  Pagefind search stays default-on.
- Splash `index.mdx`: tagline ("Build small local apps on a unified stack — no build
  tooling to manage."), hero actions → *What is Lodekit* and *SDK reference*, plus a
  three-card row (Start here / Services / Building apps) using Starlight's Card
  components.
- The old `getting-started.md` placeholder is deleted (superseded by `start/install`).

## 9. Out of scope (stays parked on roadmap)

- Deploy/hosting (`docs.lodekit.com`) and any CI for the docs build.
- Full shared design layer with the landing site; self-hosted fonts.
- Screenshots/video (no stable visual identity to capture yet — dashboard UI still
  moving); revisit post-v0.1.
- Versioned docs, i18n, changelog page.

## 10. Verification

- `pnpm --filter @lodekit/web-docs build` green (Starlight validates internal links
  and slugs at build time).
- Accuracy pass: a reviewer (subagent) checks every SDK reference page against
  `packages/sdk/src/*.ts` signatures and every stated limit against
  `packages/runtime/src/platformSettings.ts`.
- Dev-server spot-check of the splash, one Services page, one SDK page, and both
  color schemes.
- Work stays on the `docs` branch; the person reviews and folds (no unattended
  integration).

## 12. Addendum (2026-07-13): formal store titles

Person-decided naming refactor, three registers end to end:

1. **Formal titles** — Relational Data Store, Key-Value Data Store, File Store,
   Log Store, Event Store, Secret Store (Tasks/Settings/Gateways unchanged) —
   used for page titles, sidebar, headings, and first mentions.
2. **Bold short terms** — **db-store**, **kv-store**, **file-store**,
   **log-store**, **event-store**, **secret-store** — the catalog names, used
   in running prose after a first-mention introduction ("the Relational Data
   Store (**db-store** for short)"); services/overview explains the convention
   once; elsewhere a bold short term + link is the introduction.
3. **Mono** stays reserved for typed code (`db`, `kv.get()`, paths). SDK pages
   stay handle-titled.

Services slugs renamed to the short terms
(`/services/db-store/` …). The retired person-facing names (Database, KV,
Files, Logs, Events, Secrets as service names) moved to context.md Avoid
lists — context.md canon amended in the same commit so docs and vocabulary
never fork. Generic common nouns and real dashboard UI labels (the **Logs** /
**Events** / **Secrets** views) deliberately keep their words.
