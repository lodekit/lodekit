# Axis 1: Multi-writer sync

# FINDINGS

## A. SQLite-native multi-writer sync options (status as of Aug 2026)

**1. cr-sqlite (vlcn.io) — dormant core, community-patched builds, not archived.**
Repo not archived; MIT; ~3,756 stars; `pushed_at` 2026-08-10. But the last 10 commits tell the real story: a two-year gap (mid-2024 → Aug 2026), then five Aug-2026 commits from community contributors that are all build/packaging fixes (macOS headerpad, Android 16KB page alignment, iOS simulator, Windows ARM64 loadable) — no core feature work since 2024. Last tagged release line is v0.15/v0.16 era with 200+ unreleased commits. Creator Matt Wonlaw (tantaman) is now a partner at Rocicorp working on Zero. Semantics remain the best-in-class fit on paper: loadable SQLite extension, per-column LWW CRDTs on ordinary tables (`crr` tables), change extraction via `crsql_changes`, true peer↔peer merge with no server role — exactly "gateway = another engine." Runtime-agnostic: loads anywhere SQLite extensions load, including Go via cgo. Confidence: high on status facts (repo API + commit list), high on semantics (project README/docs). Sources: https://github.com/vlcn-io/cr-sqlite, https://api.github.com/repos/vlcn-io/cr-sqlite, https://github.com/tantaman, https://vlcn.io/docs/cr-sqlite/intro

**2. Turso (company) — the story split in two; the new "Turso Sync" on the Rust engine is the live path, and it self-hosts with no cloud.**
- Legacy libSQL embedded replicas: read-local, write-remote by default; offline-writes beta existed but Turso now says the local DB "often diverged and had to be re-bootstrapped." Turso's blanket recommendation (Apr 2026): use Turso (Rust rewrite), not libSQL, for sync. libSQL server (sqld) remains MIT and self-hostable. Confidence: high. Sources: https://turso.tech/blog/sync-benchmark, https://turso.tech/blog/turso-offline-sync-public-beta, https://docs.turso.tech/features/embedded-replicas/introduction
- Turso Database (formerly Limbo): MIT, ~23.8k stars, pushed daily, SQLite-compatible rewrite in Rust with MVCC/`BEGIN CONCURRENT`, CDC, and bidirectional offline sync as first-class features; explicitly **beta** ("SQLite-level reliability" is the bar, caution advised for mission-critical). Bindings directories in-repo: C, dotnet, **Go**, Java, JavaScript, Python, React Native, Rust, Tcl. In July 2026 they added an experimental Postgres wire frontend ("LLVM of databases"). Confidence: high. Sources: https://github.com/tursodatabase/turso, https://api.github.com/repos/tursodatabase/turso, https://www.theregister.com/databases/2026/07/29/after-rewriting-sqlite-in-rust-turso-turns-its-sights-on-postgres/5279835
- Turso Sync mechanics: local changes pushed as logical mutations (CDC), remote changes pulled as physical pages; remote is authoritative; conflict resolution is **last-push-wins per row** with a `transform` hook for custom merge logic. P2P sync explicitly unsupported (hub-and-spoke only). Packages: `@tursodatabase/sync` (Node), `@tursodatabase/sync-wasm` (browser); stated language priorities JS, Go, Python. Confidence: high. Source: https://turso.tech/blog/introducing-databases-anywhere-with-turso-sync
- **Self-hosted sync server exists and is open source**: `tursodb ./server.db --sync-server 0.0.0.0:8080` runs a sync server implementing the same protocol as Turso Cloud, no cloud account, no auth token locally. Glauber Costa (co-founder) publicly confirmed "fully locally, without our cloud... All Open Source" (Turso 0.5.0). Docs frame it as a *local dev/test* server, so production posture of the self-hosted server is unproven. Confidence: high that it exists/works; medium that it's a supported production gateway. Sources: https://docs.turso.tech/sync/local-sync-server, https://x.com/glcst/status/2029781200555102472

**3. ElectricSQL — pivoted; Postgres-only, read-path-only. Not a candidate.**
Post-2024-rewrite Electric is an Elixir service that syncs "Shapes" (WHERE-clause subsets) out of Postgres to clients over HTTP; writes go through your own backend API; local-first write support is an open community discussion, not a feature. Now marketed partly as an agent platform. No SQLite server side, no engine↔engine story. Confidence: high. Sources: https://github.com/electric-sql/electric, https://electric-sql.com/, https://github.com/electric-sql/electric/discussions/1684

**4. PowerSync — service-dependent, backend-DB↔SQLite, not SQLite↔SQLite.**
Requires a backend database (Postgres GA, MongoDB GA, MySQL beta, SQL Server alpha) plus the PowerSync Service; client is always SQLite. Self-hostable "Open Edition" exists but the service is **FSL source-available** (clients Apache-2.0). Writes upload to *your* backend API (server-authoritative). A gateway would have to run Postgres + PowerSync Service — violates "gateway is just another engine." Confidence: high. Sources: https://docs.powersync.com/intro/setup-guide, https://powersync.com/open-source, https://powersync.com/blog/introducing-powersync-v1-0-postgres-sqlite-sync-layer

**5. Evolu — closest philosophical match in JS; MIT relay, E2E-encrypted binary protocol, relay↔relay sync.**
TypeScript library + "Evolu Protocol": E2E-encrypted binary sync protocol "optimized for minimal size," designed for SQLite; supports client↔relay, client↔client (P2P on roadmap), and **relay↔relay**. LWW CRDT ordered by hybrid logical clocks (design descends from James Long's "CRDTs for Mortals"). Identity: symmetric keys derived from a BIP-39-style mnemonic (SLIP-21-style derivation); relay is fully blind (sees only OwnerId, timestamps, encrypted blobs), PADMÉ message padding, symmetric-only crypto (post-quantum-safe claim). Relay is MIT, self-hostable (Docker in-repo), stateless, multiple relays can load-balance by OwnerId. Constraint: it's a framework — writes must go through Evolu mutations against an Evolu-typed schema; platform targets are browsers/Electron/React Native; Node-as-client is not advertised. Confidence: high on protocol/relay/privacy claims (official docs); medium on "Node client unsupported" (absence of evidence). Sources: https://www.evolu.dev/docs/privacy, https://www.evolu.dev/docs/evolu-server, https://www.evolu.dev/, https://www.evolu.dev/docs/how-evolu-works

**6. SQLSync — effectively frozen; successor Graft is alpha.**
SQLSync (orbitinghail): last meaningful issues 2024; repo activity is CodeQL/dependabot; Carl Sverre's energy moved to Graft (announced Mar 2025), a transactional page-storage engine for lazy partial replication — explicitly "Alpha quality, contact @carlsverre before production." Neither is a credible 2026 dependency for you. Confidence: high. Sources: https://github.com/orbitinghail/sqlsync, https://github.com/orbitinghail/graft

**7. Verdant — alive but one-person, IndexedDB/web-centric.**
Grant Forrest's storage+sync framework; used in his own production apps (biscuits.club) with fuzz/integration tests, but client storage is IndexedDB (browser), not SQLite; author explicitly declines to guarantee consistency mathematically. Wrong shape for a server engine. Confidence: medium-high. Source: https://github.com/a-type/verdant

**8. Jazz (CoJSON) — MIT, self-hostable sync server, but takes over your data model.**
Open-source (MIT) toolkit; CoJSON handles co-editing, identities/accounts, permissions, sync, persistence. Self-host via `jazz-run` (WebSocket, SQLite storage at `sync-db/storage.db`, Node ≥20); can federate with Jazz Cloud. Like Evolu, adopting it means the engine's data layer becomes CoValues, not your SQLite tables. jazz-tools at 0.20.x — pre-1.0 API churn risk. Confidence: high. Sources: https://jazz.tools/docs/react/core-concepts/sync-and-storage, https://www.npmjs.com/package/jazz-tools

**9. Zero (Rocicorp) — hit 1.0 (June 2026) but requires Postgres upstream. Not a candidate.**
Zero 1.0 shipped June 2026 (InfoQ); self-hostable and open source; but zero-cache requires **Postgres ≥15 with logical replication** as the upstream source of truth (SQLite is only its internal replica format); writes go through custom mutators against your Postgres. A lodekit gateway would have to run Postgres. Confidence: high. Sources: https://www.infoq.com/news/2026/06/zero-version-1/, https://zero.rocicorp.dev/docs/connecting-to-postgres, https://zero.rocicorp.dev/docs/self-host

**10. New entrant: sqlite-sync (SQLite Cloud / sqlite.ai) — loadable extension, but Elastic License and no SQLite-server target.**
Multi-platform loadable extension turning any SQLite DB into a conflict-free offline-first replica; CRDTs (causal-length set, delete-wins, add-wins, block-level LWW for text columns). Sync targets: SQLite Cloud, or self-hosted **PostgreSQL/Supabase** — i.e., the gateway is Postgres or their cloud, not another SQLite engine. Elastic License 2.0 (not OSI; commercial license for managed-service use). Confidence: high. Source: https://github.com/sqliteai/sqlite-sync

## B. CRDT libraries

**11. Automerge 3 — shipped Aug 2025; the document-size problem is largely fixed; JS/WASM runs everywhere; Go binding is stale.**
Automerge 3.0: Rust core now uses the columnar compressed format in memory → >10x (up to ~100x) memory reduction (Moby Dick paste: 700MB in v2 → 1.3MB in v3; one 17-hour-load document now loads in 9s). Same file format as v2, near-backward-compatible API. Funded/staffed via Ink & Switch (lead maintainer Alex Good). JS is WASM-based → works in Node/Bun/Deno; a Bun-specific fork of the sync server exists, and the official self-hostable sync server is a small Node/Express WebSocket app (`automerge-repo-sync-server`); protocol also implemented outside JS (posit-dev "autosync" in R, with TLS+OIDC). **automerge-go**: official org, cgo wrapper over automerge-rs C bindings, idiomatic API — but last push **Oct 30, 2024**, i.e., pre-Automerge-3 core, ~22 months stale. Confidence: high. Sources: https://automerge.org/blog/automerge-3/, https://api.github.com/repos/automerge/automerge-go, https://github.com/automerge/automerge-repo-sync-server, https://github.com/marionauta/automerge-repo-sync-server, https://posit-dev.github.io/autosync/

**12. Loro — 1.x, very active; official Swift/Python bindings; Go binding exists but community-maintained.**
loro-crdt npm at 1.13.1 (days old as of the search); core repo ~6k stars, active July 2026. Bindings via UniFFI (loro-ffi): Swift and Python official and current (updated Jul 2026); **loro-go is listed as community-maintained** in the loro-ffi README — quality/currency unverified (repo didn't surface in direct search). JS package is WASM → Bun/Deno fine. Confidence: high on Loro core status; low on loro-go quality. Sources: https://github.com/loro-dev/loro, https://github.com/loro-dev/loro-ffi, https://www.npmjs.com/package/loro-crdt

**13. Yjs — JS-native (ideal in any JS runtime); no official yrs Go FFI binding, but two wire-compatible pure-Go ports now exist.**
y-crdt (yrs, Rust) stated Go bindings as a funding goal but never shipped them. Instead: **reearth/ygo** — pure Go, no cgo, all Y-types, V1/V2 wire formats, y-protocols sync+awareness, gomobile, in production at Re:Earth, listed on the official Yjs ports page; and **Deln0r/ygo** — pure Go, byte-for-byte wire-compatible with yjs@13.6.31 (158 cross-language fixtures), bundled Hocuspocus-compatible single-binary server with SQLite persistence (~3.5x yjs apply wall-clock). "y-sqlite" as a package doesn't really exist — SQLite persistence for Yjs is via `@hocuspocus/extension-sqlite`, y-expo-sqlite (RN), or hand-rolled update logs. Confidence: high. Sources: https://docs.yjs.dev/ecosystem/ports-to-other-languages, https://github.com/reearth/ygo, https://github.com/Deln0r/ygo, https://www.npmjs.com/package/@hocuspocus/extension-sqlite
Caveat applying to 11–13: all three are *document* CRDTs; using them for lodekit means either making documents the storage model or building a table↔doc mapping layer — they don't merge SQL rows natively.

## C. Go-side options

**14. marmot — v2 is a ground-up rewrite, leaderless gossip multi-writer, but apps must write via MySQL wire protocol; still beta.**
v2 dropped NATS/JetStream for gossip + gRPC + own 2PC; any node accepts writes; eventual consistency + anti-entropy; tunable ONE/QUORUM/ALL; DDL replicated. Critical constraint: applications connect via **MySQL protocol (port 3307)** for writes (direct SQLite reads OK). Releases v2.0.1-beta/v2.0.2-beta (Nov). Single-maintainer project. Confidence: high. Source: https://github.com/maxpert/marmot

**15. rqlite — mature and active, but CP/single-leader: no offline writes, no reconciliation. Not a fit for the north star.**
All writes through Raft leader; partitioned minority can't write; explicitly "no write scaling," HA-focused. Actively maintained in 2026 (docs indexed May 2026; CDC, auto-clustering). Useful prior art only. Confidence: high. Sources: https://rqlite.io/docs/design/, https://rqlite.io/docs/faq/

**16. LiteFS — beta, single-writer, cloud product discontinued, future uncertain.**
FUSE-based physical replication with one primary (Consul-elected); v0.5.14 (Apr 2025), pushed May 2026, still badged beta; LiteFS Cloud discontinued; community openly asking "what is the status of LiteFS." Single-writer disqualifies it anyway. Confidence: high. Sources: https://www.everydev.ai/tools/litefs, https://community.fly.io/t/what-is-the-status-of-litefs/23883

**17. Corrosion (Fly.io) — Rust (not Go), built on cr-sqlite, prod-proven and prod-scarred.**
Gossip (SWIM) service-discovery state store; each node holds SQLite; **uses cr-sqlite for CRDT conflict resolution**; Apache-2.0, 1,127 commits. But: it's a Rust daemon for cluster metadata, not an app-data sync library, and "almost every significant Fly.io incident in 2025 and 2026 traces back to Consul and Corrosion" (single global state domain mistake, being unwound; Aug 9, 2026 incident involved Corrosion retry pressure). Treat as prior art / cautionary tale for gossip-everything designs, and as evidence cr-sqlite's CRDT core works at scale. Confidence: high. Sources: https://github.com/superfly/corrosion, https://fly.io/blog/corrosion/, https://kuberns.com/blogs/is-fly-io-good-for-production/, https://status.flyio.net/

**18. Hand-rolled sync, prior art: Actual Budget's design is the canonical solo-dev-sized blueprint.**
Actual (MIT, local-first, self-hosted server): every mutation becomes a message (table, row, column, value, HLC timestamp) stored in a `messages_crdt` table alongside the applied state; last-write-wins per field ordered by hybrid logical clocks; a **Merkle trie keyed on base-3 HLC timestamps (minute resolution, XOR hashes)** finds the divergence point so reconnecting devices exchange only the delta; "the server is basically a thin client that keeps messages and moves them around" — literally the "gateway = another engine" shape. Reference implementation: jlongster/crdt-example-app (annotated fork exists); Actual maintains property-based tests over the timestamp and trie code. Data stored twice; a big budget DB is ~16MB, so overhead acceptable for personal-tool scale. Confidence: high. Sources: https://archive.jlongster.com/using-crdts-in-the-wild, https://github.com/jlongster/crdt-example-app, https://github.com/snellingio/crdt-example-app_annotated/blob/master/NOTES.md, https://imfeld.dev/writing/crdts_for_mortals, https://openapps.pro/apps/actual

## D. Identity/auth between instances (prior art)

**19. Syncthing (Go) — device ID = SHA-256 of a self-signed TLS cert; mutual TLS + allowlist.**
Each device generates a keypair + self-signed cert; the device ID is the SHA-256 hash of the cert, rendered base32 with Luhn check digits. All connections are TLS 1.2/1.3 with both sides presenting certs; at handshake the peer's cert hash is computed and compared against the preset list of accepted device IDs; unknown/duplicate IDs are dropped. Security rests on preimage resistance (attacker needs a valid signed DER cert matching the hash). Discovery is unauthenticated but harmless because impersonation fails at TLS. **Directly reusable**: Node (`tls` with client certs) and Go both support this natively; pairing = out-of-band exchange of two short strings. Confidence: high. Sources: https://docs.syncthing.net/dev/device-ids.html, https://docs.syncthing.net/users/security.html

**20. Actual Budget — server password (trusting model) + optional E2E key; Evolu — mnemonic is the identity; Obsidian LiveSync — DB credentials + separate E2EE passphrase, pairing via encrypted setup-URI.**
LiveSync's pairing pattern: first device generates an `obsidian://setuplivesync?settings=` URI containing encrypted connection credentials, protected by its own passphrase, transferred to the new device over a private channel; vault data is separately E2E-encrypted with a permanent shared passphrase (changing it = rebuild remote DB). Evolu's pattern (finding 5): possession of the mnemonic-derived key *is* identity+access; relay needs no auth at all because it's blind. Spectrum for lodekit: (a) Syncthing-style mTLS pinning for transport-level engine↔engine auth (fits a non-blind gateway that is itself an engine serving apps), plus optionally (b) Evolu-style symmetric E2E if the gateway should be blind — note a blind gateway cannot *serve* the apps, so (a) matches lodekit's gateway-is-an-engine model better. Confidence: high on the described mechanisms. Sources: https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/quick_setup.md, https://www.evolu.dev/docs/privacy, https://archive.jlongster.com/using-crdts-in-the-wild

## E. Runtime-compatibility matrix facts

**21. SQLite extension loading (matters for cr-sqlite/sqlite-sync-class options):**
- Node `node:sqlite`: supported, requires `allowExtension: true` at construction. Node 24+ has this. better-sqlite3 also loads extensions (current, v13.0.3, actively maintained).
- Bun `bun:sqlite`: `db.loadExtension()` supported, but on macOS Apple's SQLite build disables extension loading — requires `Database.setCustomSQLite("/opt/homebrew/.../libsqlite3.dylib")` (historic segfault issue #5756). better-sqlite3 on Bun hits NODE_MODULE_VERSION/ABI mismatches; Bun's own advice is bun:sqlite. Bun has initial `node:sqlite` compat since v1.1.27 (fidelity not guaranteed).
- Deno `node:sqlite`: mirrors Node's API; `loadExtension` was unimplemented as of Deno 2.3 (issue #29030); fixes landed later (PR #31455 added real loadable-extension tests after an earlier segfault); also had a permission-bypass CVE via ATTACH (CVE-2025-48935). Newest Deno should work; margin is thinner than Node.
- Go: standard `sqlite3_load_extension` via mattn/go-sqlite3 (cgo) — a loadable extension is the one artifact that works across all four runtimes.
Confidence: high (all from official docs/issues). Sources: https://bun.com/docs/runtime/sqlite, https://github.com/oven-sh/bun/issues/5756, https://nodejs.org/api/sqlite.html, https://github.com/denoland/deno/issues/29030, https://github.com/denoland/deno/pull/31455, https://github.com/oven-sh/bun/issues/16050, https://alexgarcia.xyz/sqlite-vec/js.html

**22. WASM CRDTs (Automerge/Loro) run on Node/Bun/Deno alike; native-addon SDKs (Turso's napi packages, better-sqlite3) are Node-first with Bun/Deno friction.** Confidence: medium-high (WASM portability is well-established; Turso-on-Bun/Deno specifically untested in sources). Sources: finding 11, 21.

# RANKED COMPARISON — "laptop engine + VPS gateway engine both accept writes and reconcile"

## Stay on a JS runtime (Node; mostly Bun/Deno-portable)

**JS-1. Hand-rolled per-table LWW + HLC + Merkle trie over the existing better-sqlite3 stack (Actual Budget pattern).**
Fit: perfect — the gateway is literally another engine running the same ~1–2k LOC sync module; no third-party service, no new storage engine, protocol trivially specifiable in protobuf/JSON. Prior art is MIT-licensed, annotated, property-tested, and has run in production (Actual) for years. Runtime-agnostic by construction: the *protocol* ports to Bun/Deno/Go unchanged, which decouples the sync decision from the runtime decision — the strongest strategic property of any option here. Learning/showcase value: high (HLCs, Merkle diffing, CRDT messages are teachable). Risks: you own correctness (mitigate: port jlongster's code + property tests rather than invent); LWW-per-column only (no text merging); requires all writes to flow through the SDK's mutation path (lodekit already controls the SDK). Maturity: pattern proven; your implementation new. **Recommended default.**

**JS-2. Turso stack: `@tursodatabase/database` + `@tursodatabase/sync`, gateway runs `tursodb --sync-server`.**
Fit: good — self-hosted, MIT end-to-end, no cloud (founder-confirmed), least code of any option, real offline multi-writer with last-push-wins + `transform` hook for custom merges. Big learning/showcase value (the "SQLite in Rust" story). Risks: the engine itself is **beta** (your data would live in it); the self-hosted sync server is positioned as dev/test with no auth token story (you'd wrap it behind mTLS/reverse proxy); hub-and-spoke only, remote-authoritative; replaces better-sqlite3 wholesale; Bun/Deno support of the napi package unverified. Maturity: watch-and-adopt — strongest trajectory (company-backed, 24k stars), weakest present-day stability guarantee. **Best "buy" option; adopt when it exits beta or for a non-critical concern first.**

**JS-3. cr-sqlite loadable extension + thin WebSocket transport you write.**
Fit: semantically the best (true peer↔peer per-column CRDT merge in SQL; Corrosion proves the core at scale) and runtime-agnostic including a future Go engine via cgo. Risks: dormant core since 2024, creator gone to Rocicorp, only build-fix maintenance; you'd be adopting an unowned Rust codebase; extension loading has macOS/Bun and Deno friction (finding 21). Viable only if you're willing to be the de-facto maintainer of your pinned build. **Fallback, not a foundation.**

(Non-ranked JS mentions: **Evolu** — adopt only if you accept its schema/mutation layer owning the data model; its relay+mnemonic+blind-sync design is otherwise the best thing to *steal ideas from*. **Jazz** — same shape, pre-1.0. **Automerge 3/Loro/Yjs** — only if lodekit's data model pivots to documents; all three JS bindings run fine on Node/Bun/Deno. **ElectricSQL, PowerSync, Zero** — all require Postgres (or another big backend DB) on the gateway; disqualified by "gateway = another engine.")

## Go

**Go-1. Hand-rolled HLC + LWW + Merkle trie (same protocol as JS-1), single static binary.**
Fit: identical to JS-1; Go is arguably the best implementation language for it (strong stdlib TLS for Syncthing-style identity, easy daemonization, cross-compile). Prior art ports cleanly; HLC implementations are well-trodden in Go (CockroachDB lineage). Risks: same owned-correctness burden; plus the general cost of rewriting the whole engine in Go. **Recommended default if Go wins the runtime decision.**

**Go-2. cr-sqlite extension via cgo (mattn/go-sqlite3) + own transport.**
Fit: reuses proven CRDT merge logic; extension artifact shared with any JS-runtime engine during a transition (the one genuinely runtime-agnostic sync core). Risks: cr-sqlite dormancy (finding 1) + cgo build complexity. **Credible second.**

**Go-3. (a) Turso Go bindings + sync once shipped, or (b) pure-Go Yjs ports (reearth/ygo) if the data model goes document-shaped.**
(a) `bindings/go` exists in the Turso repo and Go is a stated sync priority, but Go sync availability is unconfirmed — watch item, same beta caveats as JS-2. (b) reearth/ygo is production-used, no-cgo, wire-compatible with the whole Yjs ecosystem — the most mature *Go-native* CRDT option found, but document-model only. **marmot** (MySQL-protocol writes, beta), **rqlite** (single-leader, no offline writes), **LiteFS** (single-writer, uncertain future) all fail the multi-writer-offline requirement; **Corrosion** is Rust and ops-scarred.

## Cross-cutting recommendation for identity/auth (either runtime)
Syncthing's model is the reusable one: at engine init, generate a self-signed cert; identity = SHA-256(cert) in base32+check-digits; pairing = exchange IDs out of band; every engine↔engine connection is mutual-TLS with pinned cert hashes. Works natively in Node and Go; no accounts, no PKI, no third party. Layer Evolu-style symmetric E2E only if a blind relay tier is ever wanted (incompatible with a gateway that must itself serve apps).

# Axis 2: Windows + daemon + CLI

## Part 0: Prior internal report (2026-07-07) — what carries over

**F0.1** — The prior report (`~/Desktop/lodekit/lodekit-cross-platform-report.html`, local file) is Electron-era but several findings survive the pivot to daemon+CLI: (a) Windows was sized as the big lift (~1.5–2.5 wks: `%APPDATA%` paths, node.exe-at-dist-root layout, bundle-script shell-out rewrite, shutdown-without-signals, NSIS); (b) Node's `kill('SIGTERM')` on Windows is an unconditional `TerminateProcess` — no handler runs — and the chosen fix was a **stdin-close sentinel** with hard-kill backstop; (c) unsigned NSIS + documented SmartScreen click-through is the standard small-project Windows path, with Azure Trusted Signing (~$10/mo) as a later toggle (pricing not re-verified this session); (d) native runners per target for native modules; (e) fix MCP's broken `openInBrowser` Windows branch. Items (a)–(d) are runtime-decision inputs; the Electron packaging decisions (electron-builder migration, tray icon formats) are conditional on keeping the Electron manager, which the north star now questions. Confidence: high (primary local document).

**F0.2** — The stdin-sentinel design is independently validated: Tailscale's Windows service uses exactly this pattern — a parent `ipnService` process registered with the SCM spawns a `/subproc` child that "detects parent death via stdin EOF" and restarts on crash with exponential backoff ([DeepWiki: tailscale platform-specific implementations](https://deepwiki.com/tailscale/tailscale/6.4-platform-specific-implementations)). Confidence: medium-high (secondary source over the open-source repo; consistent with the repo's known architecture).

## Part 1: Shipping shape on Windows per runtime

**F1.1 — Node, bundled-zip shape (status quo).** Official nodejs.org dist for v24.12.0 (Lodekit's pinned version) ships `node-v24.12.0-win-x64.zip` (36 MB) and `node-v24.12.0-win-arm64.zip` (33 MB), plus x64/arm64 MSIs and all mac/linux tarballs ([nodejs.org/dist/v24.12.0/](https://nodejs.org/dist/v24.12.0/)). The prior report's `(platform, arch) → dist` table approach extends to win-arm64 for free. Node 24 is Active LTS until April 2028; Node 26 (May 2026) is Current and becomes LTS Oct 2026; from Oct 2026 Node moves to one calendar-aligned LTS release per year ([endoflife.date/nodejs](https://endoflife.date/nodejs), [nodejs.org release-schedule blog](https://nodejs.org/en/blog/announcements/evolving-the-nodejs-release-schedule)). Confidence: high.

**F1.2 — Node SEA.** Stability is **1.1 "Active development"** in current docs (was 1.2 "Release Candidate" claims in some third-party guides — the official docs page is authoritative). Node 25.5 (Jan 2026) added one-step `node --build-sea` replacing the copy-binary + postject flow ([official SEA docs](https://nodejs.org/api/single-executable-applications.html), [Joyee Cheung's blog, 2026-01-26](https://joyeecheung.github.io/blog/2026/01/26/improving-single-executable-application-building-for-node-js/)). Caveats from the official docs: CI-tested on Windows and macOS **arm64 only (mac x64 not currently supported)**; native addons work only via an assets + write-to-tmpdir + `process.dlopen` hack; Windows signing = optional `signtool remove` then `signtool sign` after injection; cross-platform SEA generation requires `useCodeCache`/`useSnapshot` false. SEA is a plausible 2027 shape, not a boring 2026 one. Confidence: high (primary docs).

**F1.3 — Bun `--compile`.** `bun build --compile --target=bun-windows-x64` produces a single exe embedding the whole Bun runtime; hello-world ≈57 MB (Bun 1.1.30 era), so expect ~60–100+ MB real apps ([bun docs](https://bun.com/docs/bundler/executables), [minimal-runtime request #14546](https://github.com/oven-sh/bun/issues/14546)). Windows-specific rough edges, all with open issues: process list shows "Bun" instead of the exe name ([#13454](https://github.com/oven-sh/bun/issues/13454)); when `node` isn't on PATH, the compiled app auto-creates a `node` shim pointing at *itself*, hijacking any `#!/usr/bin/env node` tool ([opencode #15880](https://github.com/anomalyco/opencode/issues/15880), Mar 2026); glob asset embedding broken on Windows ([#22316](https://github.com/oven-sh/bun/issues/22316)); source readable inside the binary despite minify/bytecode ([#19498](https://github.com/oven-sh/bun/issues/19498)); Windows Defender has flagged Bun binaries as trojan (false positive, [#16981](https://github.com/oven-sh/bun/issues/16981)). Cross-compilation to Windows from mac/Linux is supported via `--target`. Confidence: high on the issue list (primary issues); medium on size range.

**F1.4 — `deno compile`.** Six targets, cross-compilable from any host: win x64 + **`aarch64-pc-windows-msvc` (win-arm64, since Deno 2.9.3)**, mac x64/arm64, linux x64/arm64. **Code signing is supported**: mac binaries get an ad-hoc signature by default and accept `codesign`; Windows binaries can be signed with `signtool sign /fd SHA256` — the old "cannot be code signed" era ([#11154](https://github.com/denoland/deno/issues/11154)) is resolved. `--icon` embeds a Windows .ico, including when cross-compiling ([deno compile docs](https://docs.deno.com/runtime/reference/cli/compile/)). Size floor ~60–80 MB (Deno 2 exes ≈80 MB); known bloat bug where workspaces/monorepos embedded the entire `node_modules` (one 565 MB case), now mitigated by the `--bundle` flag which tree-shakes — at the cost of dropping non-literal dynamic `import()`/computed worker URLs ([discussion #28536](https://github.com/denoland/deno/discussions/28536), [issue #30134](https://github.com/denoland/deno/issues/30134), [dyoshikawa Deno→Bun writeup](https://zenn.dev/dyoshikawa/articles/deno-to-bun-single-binary?locale=en)). Confidence: high (primary docs) except size numbers (medium).

**F1.5 — Go.** `GOOS=windows go build` is trivial *only with pure Go*. With a cgo SQLite driver, cross-compiling to win-x64 needs mingw-w64 (`x86_64-w64-mingw32-gcc`) or `zig cc`; classic mingw-w64 **cannot target win-arm64** — you need llvm-mingw or zig. windows/arm64 (with cgo) is supported since Go 1.17 ([Go 1.17 release notes](https://go.dev/doc/go1.17), [ecostack cgo cross-compile guide](https://ecostack.dev/posts/go-and-cgo-cross-compilation/), [goreleaser zig-cgo example](https://github.com/goreleaser/example-zig-cgo)). With modernc (pure Go, F3.5), all six targets build from one machine with zero extra toolchain. Binary size ~15–30 MB. Confidence: high.

## Part 2: Daemon/service story

**F2.1 — The key pattern discovery: for single-user localhost tools, the industry norm on Windows is *login-scoped autostart*, not a Windows Service.** Syncthing's official docs: "Starting Syncthing on login is the preferred approach for almost any end-user scenario"; a service (via NSSM) is "only" sensible for "(mostly) headless servers, administered by a sysadmin who knows enough to understand the security implications" ([syncthing autostart docs](https://docs.syncthing.net/users/autostart.html)). Ollama on Windows registers **no service at all** — `ollama app.exe` sits in the Startup folder, launches at login, supervises and respawns `ollama.exe serve` ([#10713](https://github.com/ollama/ollama/issues/10713), [#14761](https://github.com/ollama/ollama/issues/14761)). Ollama and Syncthing are both Go, so this is a product choice, not a runtime limitation. Tailscale ships a real SCM service ("Tailscale", `net start/stop Tailscale`) because it needs pre-login networking and a privileged TUN device — needs Lodekit does not have ([tailscaled docs](https://tailscale.com/docs/reference/tailscaled)). Jellyfin's NSIS installer offers *both*: optional service install (`JellyfinServer`, LocalSystem/NetworkService) plus a tray app that starts the service if present, else launches the exe directly ([jellyfin-server-windows](https://github.com/jellyfin/jellyfin-server-windows)). Home Assistant has no native Windows story at all (VM only; Supervised deprecated 2025) ([HA deprecation post](https://www.home-assistant.io/blog/2025/05/22/deprecating-core-and-supervised-installation-methods-and-32-bit-systems/)). Implication: Lodekit's Windows "daemon" can be a login-scoped background process + tiny supervisor (Ollama model) on any of the four runtimes; a true SCM service is optional hardening, not table stakes. Confidence: high.

**F2.2 — True SCM services per runtime.** Go: native and mature — `golang.org/x/sys/windows/svc` (what Tailscale uses) or **kardianos/service** (Windows SCM + launchd + systemd/OpenRC behind one API; 4.8k stars, not archived, pushed July 2026, used via forks by k0s, GitLab Runner, Percona) ([kardianos/service](https://github.com/kardianos/service), [GitHub API](https://api.github.com/repos/kardianos/service)). Node/Bun/Deno: **none of the three JS runtimes can talk to the SCM natively.** Bun has an open enhancement request (Jan 2026) explicitly stating compiled exes "cannot be registered as true Windows services" and naming NSSM/WinSW/Task Scheduler as the workarounds ([bun #25824](https://github.com/oven-sh/bun/issues/25824)). Node's ecosystem answer is `node-windows` (wraps WinSW; last npm publish ~4 years ago, still 1.0.0-beta.8) or WinSW/NSSM directly ([node-windows](https://github.com/coreybutler/node-windows), [npm](https://www.npmjs.com/package/node-windows)). Deno has a community FFI-based `windows_service` module (requires `--unstable --allow-ffi`, niche) or the same wrappers ([deno windows_service](https://deno.land/x/windows_service@1.0.11)). Confidence: high.

**F2.3 — Wrapper health check.** NSSM: abandoned (last release 2017, flagged Discontinued). WinSW: disputed — functional and widely deployed (Jenkins), v2.12 (2023) stable, v3 stuck in pre-release; independent sources call it maintained, competitors call it "maintenance limbo". Newer maintained options: Shawl (single Rust binary, winget, v1.7.0 Jan 2026) and Servy ([winsw/winsw](https://github.com/winsw/winsw), [Servy comparison — note: competitor marketing](https://dev.to/aelassas/servy-vs-nssm-vs-winsw-2k46), [hartiga.de Server 2025 guide](https://hartiga.de/it-architecture/service-on-windows-server-2025/)). Building the Windows-service path on any JS runtime means adopting one of these as a load-bearing dependency. Confidence: medium-high.

**F2.4 — macOS/Linux daemon story is runtime-neutral.** launchd LaunchAgent plists and systemd (user or system) units exec any binary; Ollama's Linux install script creates `ollama.service` + dedicated user via systemd ([docs.ollama.com/linux](https://docs.ollama.com/linux)); tailscaled runs as launchd service on mac (non-GUI) and systemd on Linux ([tailscaled docs](https://tailscale.com/docs/reference/tailscaled)). No candidate has an advantage here except Go's kardianos/service giving all three OSes one API. Confidence: high.

## Part 3: SQLite on Windows per runtime

**F3.1 — better-sqlite3 (status quo).** Prebuilds exist for win-x64; win-arm64 prebuilds are in the matrix but historically flaky ("flaky-release" label; specific combos 404 and fall back to source-compile requiring MSVC) ([#1192](https://github.com/WiseLibs/better-sqlite3/issues/1192), [#769](https://github.com/WiseLibs/better-sqlite3/issues/769)). This is the ABI-pinning pain Lodekit already carries (pinned Node 24.12.0). Confidence: medium-high.

**F3.2 — node:sqlite.** In Node 24.x LTS: **Stability 1.2 "Release Candidate", no flag required** ([v24 docs](https://nodejs.org/docs/latest-v24.x/api/sqlite.html)). Full-featured: prepared statements, UDFs/aggregates, extensions, serialize/deserialize, async backup, sessions/changesets; no platform caveats documented — it's compiled into node.exe, so Windows/arm64 work wherever Node does ([node:sqlite docs](https://nodejs.org/api/sqlite.html)). **Migrating engine SQLite access from better-sqlite3 to node:sqlite would delete the only native module in the payload, ending the ABI-pinning constraint and making the Windows/arm64 story pure-zip.** Lodekit already has a `sqlite.ts` seam (recent PR #141/#203 per git log). Confidence: high.

**F3.3 — bun:sqlite.** Built into the runtime, no addon; Bun statically links its own SQLite on Linux and Windows (macOS uses system SQLite — extension loading there needs Homebrew SQLite + `Database.setCustomSQLite`); WAL supported; works inside compiled executables (part of the runtime) ([bun:sqlite docs](https://bun.com/docs/api/sqlite)). Confidence: high (docs), medium on --compile interaction (inference, not doc-stated).

**F3.4 — Deno node:sqlite.** Shipped in Deno 2.2 (Feb 2025), actively aligned with Node's test suite since; known gaps: `backup()` missing, `DatabaseSync` path won't take ArrayBuffer ([Deno 2.2 blog](https://deno.com/blog/v2.2), [#29439](https://github.com/denoland/deno/issues/29439)). Built-in, so no Windows-specific concerns. Confidence: high.

**F3.5 — Go.** mattn/go-sqlite3 (cgo) is the de-facto standard but poisons cross-compilation (F1.5). modernc.org/sqlite (pure Go, sponsored maintainer) is production-viable, used widely (e.g., zombiezen driver builds on it), roughly 1.1–2× slower than cgo — DataStation's benchmark found ≥2× slower with worse tails; fine for single-user workloads ([modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite), [DataStation benchmark](https://datastation.multiprocess.io/blog/2022-05-12-sqlite-in-go-with-and-without-cgo.html), [oneuptime 2026 guide](https://oneuptime.com/blog/post/2026-02-02-sqlite-go/view)). A third option, ncruces/go-sqlite3 (real SQLite via wasm), also avoids cgo. Confidence: high.

## Part 4: CLI controller patterns

**F4.1 — Three reference structures.** (a) **Syncthing: single binary, subcommand dispatch** — bare `syncthing` defaults to `serve`; `syncthing cli` wraps the daemon's REST API with auth handled for you ([syncthing docs](https://docs.syncthing.net/users/syncthing.html)). (b) **Tailscale: two binaries** — `tailscaled` (daemon) + `tailscale` (CLI as a LocalAPI client over a platform socket; ffcli subcommands `up`/`set`/`status`); Windows GUI is a separate closed-source tray exe talking to the same LocalAPI; notably Tailscale *deliberately split* the tray GUI out of the service binary because Windows PE headers force a GUI-vs-console choice per exe ([DeepWiki CLI architecture](https://deepwiki.com/tailscale/tailscale/6.1-tailscale-cli-architecture), [tailscale #1232](https://github.com/tailscale/tailscale/issues/1232)). (c) **Ollama: single CLI binary (`ollama serve|run|…`) + separate GUI supervisor** (`ollama app.exe`) ([#14761](https://github.com/ollama/ollama/issues/14761)). For Lodekit — engine already speaks HTTP on localhost — the Syncthing model (one entrypoint, `lodekit serve` as the daemon mode, other subcommands as HTTP clients of it) is the fewest-moving-parts fit; the PE-header GUI/console constraint (#1232) is a concrete reason to keep any future tray helper as a separate exe from the daemon/CLI on Windows. Confidence: high.

## Part 5: Windows ARM64 (Snapdragon)

**F5.1** — All four candidates now have first-class win-arm64 as of mid-2026, with varying maturity: **Node** — official win-arm64 zips/MSIs on nodejs.org (F1.1; mature). **Go** — windows/arm64 since Go 1.17, cgo included; cross-compiling cgo to it needs llvm-mingw/zig, pure Go needs nothing (F1.5; mature). **Deno** — `aarch64-pc-windows-msvc` compile target since 2.9.3 (recent; F1.4). **Bun** — native `bun-windows-aarch64` first shipped in v1.3.10, early 2026; ecosystem still catching up (setup-bun still falls back to x64, [#164](https://github.com/oven-sh/setup-bun/issues/164)); before that, arm64 users ran x64 under emulation (newest; F1.3, [bun #9824 closed](https://github.com/oven-sh/bun/issues/9824)). better-sqlite3 win-arm64 prebuilds are the flaky part of the Node story (F3.1) — avoided entirely by node:sqlite. Confidence: high for Node/Go/Deno; medium-high for Bun (version-specific claim from search results, not verified against release notes directly).

## Ranking: "ship a reliable 3-OS daemon + CLI with the fewest moving parts"

Scoped strictly to this axis (packaging/daemon/CLI mechanics — not migration cost, not app-runtime compatibility, which other axes must weigh):

**1. Go.** Recipe: single binary per target (`lodekit.exe` ~15–30 MB), modernc.org/sqlite (no cgo), cross-compile all 6 targets from one CI job, kardianos/service (or x/sys/windows/svc) for SCM + launchd + systemd behind one API, Syncthing-style subcommands, unsigned-NSIS-or-just-a-zip + winget later. Every reference product on the target pattern (Tailscale, Syncthing, Ollama) is Go — the path is fully paved. **Weakest link (on-axis):** committing to modernc means accepting ~1.1–2× slower SQLite or reintroducing a cross-compile toolchain (zig/llvm-mingw) for cgo. **Weakest link (off-axis, must be flagged):** Lodekit's engine exists to *run the person's TypeScript apps*; a Go engine either embeds a JS engine or shells out to a bundled Node — which reimports the exact moving parts Go was chosen to remove. Go's #1 here is real but conditional on the other axes solving JS-app execution.

**2. Deno (best JS-runtime shape on this axis).** Recipe: `deno compile --target {6 targets}` from one host → one ~80 MB signed-able exe per OS/arch (`signtool` on Windows, ad-hoc codesign on mac), `--icon` for Windows, node:sqlite built in, subcommand CLI in the same binary, daemon = login autostart (mac LaunchAgent, Linux systemd user unit, Windows Startup/Task Scheduler) with WinSW/Shawl as the optional true-service tier. **Weakest link:** no native SCM story (wrapper dependency for real services); `deno compile`-specific bug surface (`--bundle` drops dynamic imports/computed worker URLs — relevant to an engine that loads user apps dynamically; monorepo embed bloat); node:sqlite gaps (`backup()`); and the whole engine (tsx/worker-per-app model) must be revalidated under Deno's Node-compat layer.

**3. Node (most reliable; most pieces).** Recipe today: bundled-zip — per-target official node.exe + pnpm-deployed payload, migrate engine to node:sqlite to delete the last native module (then win-arm64 is free), a small launcher/CLI (`lodekit.cmd`/shell shim or a tiny compiled shim) providing `serve|status|stop`, daemon = login autostart everywhere + WinSW for the service tier, unsigned NSIS per the prior report. Recipe later: SEA via `--build-sea` once it leaves "Active development" (watch mac-x64 support). **Weakest link:** no boring single-file story yet — the ship is a directory tree plus a wrapper for services, i.e., the most moving parts of the four; SEA fixes that but isn't stable, and node:sqlite is RC-not-stable (though unflagged in LTS). Counterweight the synthesizer should hold: it's the only candidate with zero runtime-migration risk, which "reliable" arguably weighs heavier than part count.

**4. Bun.** Recipe: `bun build --compile --target=bun-windows-x64` (+ aarch64 since 1.3.10) → single exe, bun:sqlite built in, same autostart/wrapper daemon story as Deno. **Weakest link:** Windows finish quality — process identity shows "Bun", the self-referential `node` shim footgun, glob-embed bug, readable source in the binary, Defender false positives, and the SCM gap is an open request rather than a wrapper-accepted norm. The single-binary + built-in-SQLite shape is genuinely attractive, but on a "reliable, resilient" criterion Bun's Windows track record is the least proven of the four in Aug 2026.

**Cross-cutting conclusion for the synthesizer:** the daemon question is less runtime-differentiating than expected, because the industry answer for this product class on Windows is a login-scoped supervised process (Ollama/Syncthing pattern), which every candidate can do; true SCM services are where Go alone is native and all JS runtimes share a wrapper dependency. The sharper differentiators on this axis are (a) single-binary shipping shape (Go ≫ Deno > Bun > Node-today), (b) Windows polish/AV/signing maturity (Go/Node > Deno > Bun), and (c) whether SQLite is inside the runtime (Bun/Deno/Node-via-node:sqlite yes; Node-via-better-sqlite3 and Go both reintroduce build-matrix pain).

## Open questions

1. Whether `deno compile --bundle`'s dynamic-import limitations break Lodekit's per-app worker loading model (engine loads arbitrary user app entrypoints at runtime — likely needs the non-`--bundle` mode or on-disk apps outside the binary; untested).
2. Bun/Deno equivalence for the engine's `worker_threads`-per-app architecture (out of this axis; needs the runtime-compat axis).
3. WinSW v3 trajectory — whether to bet on WinSW 2.x, Shawl, or skip the service tier entirely at v1 (F2.3 sources conflict).
4. Node SEA stability timeline — whether `--build-sea` reaches Stability 2 in Node 27 (Oct 2026 model change), which would move Node's shape from "directory tree" to "single binary" and likely change this ranking.
5. Azure Trusted Signing current pricing/eligibility for individual developers (prior report's ~$10/mo claim not re-verified; eligibility rules for non-organizations have shifted historically).
6. Whether node:sqlite (RC) performance and feature coverage match Lodekit's actual better-sqlite3 usage surface (needs a local audit of the `sqlite.ts` seam, not web research).
7. Defender/SmartScreen behavior for *signed* Bun/Deno compiled binaries specifically (reports found are mostly about unsigned artifacts; signing may largely neutralize F1.3's AV finding — unverified).

# Axis 3: API contract (ConnectRPC vs split contracts)

# FINDINGS

## A. ConnectRPC state (Aug 2026)

**A1. connect-es is stable at 2.x; no new major version.** Connect-ES 2.0 went GA November 2024 (Protobuf-ES 2.0 based, messages are plain TS types, `createClient` rename, Node >= 18.14.1). Since then only maintenance releases; latest observed is `@connectrpc/connect` 2.1.2, published ~June 2026, ~3.6M weekly downloads. Recent fixes: TS 5.9 `Uint8Array<ArrayBuffer>` compat, HTTP/2 GOAWAY handling, Http2SessionManager memory leak. Sources: https://buf.build/blog/connect-es-v2, https://github.com/connectrpc/connect-es/releases, https://www.npmjs.com/package/@connectrpc/connect. Confidence: high (version number medium-high — releases page fetch failed, version from npm search snapshot).

**A2. Still no official Hono adapter — but the null hypothesis's framing overstates the cost now.** Official server adapters remain connect-node/fastify/express/next only. However, connect-es exposes `universalServerRequestFromFetch` / `universalServerResponseToFetch` in `@connectrpc/connect/protocol`, and Cloudflare's 2026 blog shows a full Connect server on the fetch API in ~15 lines (createConnectRouter → map handlers by requestPath → convert Request/Response). Since Hono is pure Web-Standard Request/Response (`c.req.raw`), mounting Connect inside Hono is a small in-repo shim, not a missing capability. No community `connect-hono` npm package emerged. Sources: https://github.com/connectrpc/connect-es/blob/main/README.md, https://blog.cloudflare.com/grpc-workers/, https://github.com/connectrpc/connect-es/issues/550, https://hono.dev/docs/concepts/web-standard. Confidence: high.

**A3. Connect's JSON mapping: unary is fully plain-fetch consumable without any protobuf runtime; streaming is not.** Per the protocol spec: unary = plain `POST /pkg.Service/Method` with `Content-Type: application/json` body, JSON response; `Connect-Protocol-Version: 1` header "should" be sent; side-effect-free methods support plain GET with the message in query params ("can be viewed in a browser tab"). So an MCP server could call Connect unary endpoints with bare fetch + JSON, zero codegen. But server-streaming uses `application/connect+json` with enveloped binary framing (1 flag byte + 4-byte big-endian length per message, EndStream flag) — not consumable without implementing the framing or pulling the client library. This confirms the internal research's streaming point while softening the unary point. Source: https://connectrpc.com/docs/protocol/. Confidence: high.

**A4. connect-go: stable, DX materially improved in 2026.** connect-go remains the reference implementation, 1.x semver-stable ("will not make breaking changes in 1.x"). A 2026 release added the `simple` flag to protoc-gen-connect-go — generates clients/handlers without the `connect.Request`/`connect.Response` wrappers, headers via context — directly addressing the long-standing verbosity complaint. Also: Go 1.24+ baseline, dropped golang.org/x/net/http2 dep, Edition 2024 support. Sources: https://github.com/connectrpc/connect-go/releases, https://github.com/connectrpc/connect-go. Confidence: high.

**A5. protovalidate now has first-class TypeScript.** Protovalidate hit v1.0 (Go/Java/Python/C++/TypeScript, CEL-based, consistent cross-language). `@bufbuild/protovalidate` is at 1.2.0 (~May 2026), with TS type-narrowing to a `Valid` variant post-validation. Requires the `@bufbuild/protobuf` runtime. This is a change vs. the July research: proto-side validation for TS is no longer a gap. Sources: https://buf.build/blog/protovalidate-v1, https://www.npmjs.com/package/@bufbuild/protovalidate, https://github.com/bufbuild/protovalidate-es. Confidence: high.

**A6. buf CLI weight/ergonomics: fine as a dev-time tool, zero runtime footprint.** buf is a single static Go binary; v2 `buf.gen.yaml` holds inputs and plugin flags (no Makefile wrappers), managed mode keeps language options out of .proto files, remote plugin calls are batched. The only runtime dependency codegen imposes on JS clients is `@bufbuild/protobuf`, which is tree-shakeable ESM with a maintained bundle-size benchmark (Buf's own app: generated code + runtime ≈ 15% of bundle after migration; vs google-protobuf's ~50KB gzipped monolith). The dependency-light concern is real only for the MCP client package — and per A3, unary consumption needs no runtime at all. Sources: https://buf.build/blog/buf-cli-next-generation, https://buf.build/docs/configuration/v2/buf-gen-yaml/, https://github.com/bufbuild/protobuf-es/tree/main/packages/bundle-size, https://buf.build/blog/protobuf-es-v2. Confidence: high on architecture, medium on exact sizes.

## B. Realtime

**B1. Connect still has no WebSocket story; none is coming.** Open request connectrpc.com#273 remains open; bidi streaming requires end-to-end HTTP/2; maintainer-adjacent speculation points at WebTransport, not WebSockets, as the eventual path. Server-streaming and unary work over HTTP/1.1. Note for lodekit: a local Go↔Go engine sync link can do Connect bidi over h2c trivially (no proxies in the path); a browser client cannot do bidi without HTTP/2 end-to-end. Sources: https://github.com/connectrpc/connectrpc.com/issues/273, https://connectrpc.com/docs/faq/, https://connectrpc.com/docs/web/choosing-a-protocol/. Confidence: high.

**B2. Comparable products overwhelmingly use WebSocket + custom (often binary) protocol for sync, and plain HTTP streams for agent/serving surfaces.** Figma: WebSocket + optimized binary diffs/ops, deliberately not full CRDT. Linear: custom WebSocket sync engine (multiple retrospectives on scaling it). tldraw sync: WebSocket, JSON messages. Meanwhile MCP itself (see C1) moved the other way for the agent surface: stateless HTTP, streams only as POST-response bodies, removed SSE resumability, deprecated the standalone SSE transport. Pattern: sync = WS + purpose-built protocol; agent/API surface = plain stateless HTTP. Sources: https://medium.com/frontend-simplified/deconstructing-the-magic-how-figma-achieved-seamless-real-time-multi-user-collaboration-37347f2ee292, https://linear.app/blog (scaling sync engine), https://tldraw.substack.com/p/announcing-tldraw-sync, https://modelcontextprotocol.io/specification/2026-07-28/changelog. Confidence: high on the pattern, medium on individual product details.

## C. MCP ecosystem drift

**C1. MCP 2026-07-28 shipped (final, ~2 weeks ago) and it doubles down on JSON Schema — the JSON-Schema-native premise is now stronger, not weaker.** Verified from the official changelog: tool `inputSchema`/`outputSchema` loosened to full JSON Schema 2020-12 (composition, conditionals, $ref/$defs; SEP-2106) — still JSON Schema, now more of it. Other majors: protocol made stateless (no initialize handshake, no Mcp-Session-Id, capabilities in `_meta`), new `server/discover`, `subscriptions/listen` long-lived POST-response stream replaces the GET endpoint and resource subscribe/unsubscribe, SSE resumability removed, HTTP+SSE transport formally Deprecated, Tasks moved to an official extension with polling, MRTR pattern replaces server-initiated sampling/elicitation requests, Roots/Sampling/Logging deprecated, resource-not-found error now -32602. No mention of protobuf or any alternative schema format anywhere. Sources: https://modelcontextprotocol.io/specification/2026-07-28/changelog, https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/. Confidence: high.

**C2. OpenAPI→MCP generation is a mature, crowded market.** Speakeasy (self-hosted TS servers from OpenAPI, `x-speakeasy-mcp` customization, MCPB one-click bundles), Gram (Speakeasy's hosted platform), Stainless (MCP server inside the generated SDK — notably now shipping just TWO tools: a sandboxed code-execution tool over the SDK + a docs-search tool), FastMCP (Python), openapi-mcp-generator (open-source TS CLI). Sources: https://www.speakeasy.com/blog/comparison-mcp-server-generators, https://www.stainless.com/docs/compare/speakeasy/. Confidence: high.

**C3. proto→MCP tooling has emerged — but effectively Go-only.** New since the internal research's frame: redpanda-data/protoc-gen-go-mcp generates MCP servers from gRPC **or ConnectRPC** services (auto-generates JSON Schemas from method input descriptors, MCP-library-agnostic between official go-sdk and mark3labs/mcp-go, powers Redpanda Cloud's production MCP server); grpc-mcp-gateway (protoc plugin, Go/Python/Rust/C++, full spec coverage incl. prompts/resources/elicitation, Buf-published proto extensions, updated Feb 2026); stablekernel Topeka; Google published "gRPC as a custom transport for MCP" (Jan 2026). No TypeScript proto→MCP generator found. Sources: https://github.com/redpanda-data/protoc-gen-go-mcp, https://github.com/the-protobuf-project/grpc-mcp-gateway, https://cloud.google.com/blog/products/networking/grpc-as-a-native-transport-for-mcp, https://www.redpanda.com/blog/turn-grpc-api-into-mcp-server. Confidence: high on existence/features, medium on relative maturity.

**C4. Official MCP Go SDK is production-grade.** modelcontextprotocol/go-sdk v1.0.0 stable (maintained with Google, no-breaking-changes guarantee), v1.5.0 Apr 2026 (client OAuth), v1.7.0+ supports the 2026-07-28 spec. Removes any "Go is second-class for MCP" concern. Source: https://github.com/modelcontextprotocol/go-sdk/releases/tag/v1.0.0, https://github.com/modelcontextprotocol/go-sdk. Confidence: high.

**C5. The "code mode" shift is the biggest drift affecting contract design.** Cloudflare Code Mode (Sep 2025, updated Feb 2026): "LLMs are better at writing code to call MCP than at calling MCP directly" — convert tools into a typed TS API, agent writes code in a sandbox; whole Cloudflare API in ~1,000 tokens via `search()` + `execute()`. Anthropic's "Code Execution with MCP" (Nov 2025): 150K→2K tokens (98.7% reduction). Stainless already ships this as its default MCP architecture (C2). Implication: the artifact that increasingly matters for agents is a **typed, code-callable SDK with searchable docs**, not one-tool-per-endpoint — which weakens "OpenAPI vs proto" as the decisive question and strengthens "whichever stack generates the best typed TS surface". Sources: https://blog.cloudflare.com/code-mode-mcp/, https://www.marktechpost.com/2025/11/08/anthropic-turns-mcp-agents-into-code-first-systems-with-code-execution-with-mcp-approach/. Confidence: high on the trend, medium on how fast it displaces classic tool-calling.

## D. The Go angle

**D1. Go + Connect gives one schema fanning out to all four lodekit consumers, with tooling that did not cohere a year ago.** The full chain now exists: `.proto` (+protovalidate rules) → connect-go server (`simple` flag DX) → vanguard-go in-process REST transcoding via `google.api.http` (no proxy hop; REST+gRPC+gRPC-Web+Connect from one handler) → protoc-gen-connect-openapi (OpenAPI 3.1 from protos, understands protovalidate annotations) → protoc-gen-go-mcp (MCP tools for the agent) → protoc-gen-es + connect-query (typed TS client for the SPA). Sources: https://github.com/connectrpc/vanguard-go, https://github.com/sudorandom/protoc-gen-connect-openapi, plus C3/A4. Confidence: high on each piece existing; medium on integration smoothness (no single source shows all six wired together).

**D2. The generated TS client story is solid: connect-query v2.x on TanStack Query v5.** `@connectrpc/connect-query` 2.2.0 (v2.1.1 July 2026 — actively maintained, tracks tanstack query-core behavior), framework-agnostic core + React package + protoc plugin; Protobuf-ES v2 messages are plain TS types (serializable across RSC boundaries etc.). Sources: https://github.com/connectrpc/connect-query-es/releases, https://www.npmjs.com/package/@connectrpc/connect-query, https://connectrpc.com/docs/web/query/getting-started/. Confidence: high.

**D3. Hono's hc typed client has documented scaling problems right around lodekit's size (~110 routes).** Hono's own docs concede "the more routes you have, the slower your IDE" from massive type instantiation; issue #3869 reports an 8-minute CI compile from route-type accretion; generic response types break inference (#3738); and the client type structurally requires compiling the entire server (ORM types included) into the frontend's type graph. Mitigations exist (project references, pre-computed `hcWithType`), but this is a real DX tax that generated Connect clients don't pay — codegen moves the cost to a build step and severs the type coupling. Sources: https://hono.dev/docs/guides/rpc, https://github.com/honojs/hono/issues/3869, https://github.com/honojs/hono/issues/3738. Confidence: high.

**D4. Does Go+Connect beat Hono+zod+hc for a solo dev? Qualified yes under the north star, no as a pure like-for-like.** Points for Go+Connect: single-binary deployment story (relevant to the manager bundling pain with better-sqlite3 ABI), one contract → four consumers, D3's type-scaling tax avoided, MCP Go SDK stable, proto→MCP generation exists only in Go. Points against: codegen loop (buf generate on every schema change) vs zod's zero-step inline iteration; a full rewrite of ~110 routes; the 2026 comparison literature still recommends TS-native RPC for pure-TS monorepos consumed by your own frontend. Sources: D1–D3, https://www.pkgpulse.com/guides/hono-rpc-vs-trpc-vs-ts-rest-type-safe-api-clients-2026. Confidence: medium (judgment call on top of high-confidence inputs).

## E. Schema-first vs code-first with an AI agent as the main developer

**E1. 2026 writing converges on: the spec IS the runtime interface for agents, and drift is the killer.** Practitioner guidance: agents reason over the contract, so it must be complete, accurate, token-budgeted, consolidated (few domain-centric operations, not 100 granular endpoints), with structured RFC-7807-style recoverable errors; "a specification that lags production trains the agent to be confidently wrong" (75% of production APIs drift from their specs per APIContext). Academic: arXiv 2603.13404 (controlled study, schema-first tool APIs reduce tool misuse and improve recovery), arXiv 2605.10555 (Agent-First Tool API paradigm). Sources: https://www.kleinloog.ch/articles/designing-apis-for-ai-agents-as-first-class-citizens/, https://www.digitalapi.ai/blogs/how-to-make-your-apis-ready-for-ai-agents, https://arxiv.org/pdf/2603.13404, https://arxiv.org/pdf/2605.10555. Confidence: high that this is the consensus; medium on the arXiv papers' strength (abstracts only).

**E2. Application to lodekit's "agent is the developer" case (analysis, not sourced).** Schema-first (proto): the contract is a small set of agent-readable, diffable files the agent edits before implementing — codegen mechanically enforces spec/implementation agreement (zero drift by construction), and CEL validation rules live in the same file. Code-first (zod inline): zero-latency iteration, no toolchain, but the contract is smeared across ~110 route definitions and the OpenAPI artifact is derived — drift is prevented only if generation stays wired into CI. The drift argument favors schema-first more for an agent developer than a human one (agents regenerate reliably but also hallucinate endpoints that specs would have caught). Counterweight from C5: if agents consume the engine via code-mode/typed SDK anyway, both paths can produce that SDK. Confidence: medium (reasoned synthesis).

**E3. zod 4 + hono-openapi is healthier than at the time of the internal research.** zod 4 has native `z.toJSONSchema`; hono-openapi 1.x supports Standard Schema (zod/valibot/arktype/typebox), with known warts (Date unrepresentable → override to string/date-time). The incumbent path is not decaying. Sources: https://hono.dev/examples/hono-openapi, https://github.com/rhinobase/hono-openapi/issues/196, https://www.speakeasy.com/openapi/frameworks/zod/. Confidence: high.

# RECOMMENDATION MATRIX

**Outcome 1 — stay JS (Node/Bun/Deno, Hono stays):** **(a) split contracts.** The null hypothesis survives August 2026 nearly intact for this branch: MCP just re-committed to JSON Schema 2020-12 (C1); there is still no official Connect Hono adapter (A2) and no TS proto→MCP generator (C3); Connect streaming still replaces SSE with enveloped framing for zero agent gain (A3, B1). Keep Hono+zod+OpenAPI as the agent-facing public contract; keep SSE for dashboard realtime (it matches MCP's own direction, B2/C1); introduce protobuf **only** for engine↔engine sync over WebSocket (protobuf-es v2 runtime is small and tree-shakeable, buf is dev-time only — A6, B2). Two updates to the internal research record: (i) protovalidate-es v1 exists, so "no TS validation story" is stale; (ii) "Connect locks out plain clients" is wrong for unary — plain fetch+JSON and even GET work — so a future Connect surface would not be hostile to the MCP client; it just still buys the agent nothing.

**Outcome 2 — Go rewrite:** **(b) ConnectRPC everywhere.** The calculus genuinely flips: connect-go is the reference implementation with 2026 DX improvements (A4); one proto schema fans out to REST/OpenAPI (vanguard + protoc-gen-connect-openapi), MCP (protoc-gen-go-mcp — Go-only tooling, D1/C3), the SPA (protoc-gen-es + connect-query, D2), and sync (proto natively). Split contracts under Go would mean hand-maintaining an OpenAPI/JSON layer that vanguard can transcode automatically. Realtime: Connect server-streaming for the dashboard (connect-web handles enveloping), protobuf-over-WebSocket or Connect bidi over h2c for engine↔engine (local network, no proxy constraint — B1/B2). The agent still talks JSON: either through the generated MCP server or plain-fetch unary Connect (A3). Learning/showcase value is highest here, and it dissolves the hc type-scaling tax (D3) and the native-module bundling pain.

**(c) hedge worth naming:** under either runtime, invest in the code-mode-shaped agent surface (one searchable, typed, consolidated SDK surface rather than 110 tools — C5, E1). This is contract-architecture-neutral and is where the ecosystem is visibly heading.

**What would change the answer:** (1) MCP adopting a non-JSON-Schema format or a binary transport — no sign, opposite direction confirmed (C1); (2) an official connect-es fetch-server/Hono adapter or a TS proto→MCP generator appearing — would let stay-JS adopt Connect cheaply, watch connect-es releases; (3) sync design landing on an off-the-shelf CRDT engine (automerge/loro/tldraw-style) whose wire format makes the protobuf question moot; (4) code-mode becoming the dominant MCP consumption pattern faster than expected — collapses the decision to "which stack generates the best TS SDK", where Connect's generated clients are stronger than hc at this route count (C5, D2, D3).

## Part 1 — Numbered findings

### RQ1: What must still execute user code, and the four options

**Finding 1 — Under SPA-only, the remaining user-code surfaces are exactly two: scheduled tasks, and (optionally) small server extensions (custom endpoints/webhook receivers).** Everything else the prior report enumerated (validation, aggregation, secret-bearing calls, background work, inbound webhooks) is absorbable by engine primitives (scoped API, SQL, gateways with server-side credential injection, cron, inbound-gateway). This matches the 07-19 report's §3 enumeration, which survives re-examination. Confidence: high (analysis, anchored in the prior report's walkthrough of the Greenhouse checklist).

**Finding 2 — Option (a) embedded JS: goja is production-proven for exactly this product shape; its dialect ceiling is the real cost.**
- goja (dop251/goja) is actively maintained (commits 2026-08-06, 2026-07-23; min Go 1.25): https://github.com/dop251/goja. Full ES5.1; "most of ES6, work in progress." Verified via GitHub API: **async/await implemented** (issue #460 closed 2022-12-24), **generators implemented** (#436 closed 2023-02-01), **optional chaining implemented** (#350 closed 2022-01-04), **ES modules still open** (#430). No JIT; ~10–50x slower than V8 — irrelevant for I/O-bound tasks where the host does the I/O. Confidence: high (primary API data).
- **grafana/sobek** is the maintained fork with experimental ESM support, synced with upstream goja (last merge 2026-07-27), and is what k6 runs on since v0.52: https://github.com/grafana/sobek, https://github.com/grafana/k6/issues/3773. Confidence: high.
- **PocketBase is the decisive precedent**: 60.4k-star, single Go binary + SQLite (modernc) + goja "jsvm" running user-written `.pb.js` hooks and cron jobs, with a prewarmed pool of 15 runtimes claimed at parity with Go handlers for I/O-bound work: https://pocketbase.io/docs/js-overview/, https://pkg.go.dev/github.com/pocketbase/pocketbase/plugins/jsvm, https://github.com/pocketbase/pocketbase. PocketBase is still v0.39.x (July 2026), pre-1.0 but shipping every ~5 days. Its documented caveats are the honest preview of lodekit's: no `setTimeout`/`setInterval`, CJS only (ESM must be prebundled), no Node/browser APIs (`fs`, `fetch`, `window`), TS not executed directly (ambient type declarations for editor support only). Confidence: high.
- **TS story:** goja does not run TS; but the agent *always* has a toolchain — the sanctioned contract becomes "agent bundles task code to a single CJS/ES2017-ish file" (esbuild one-liner). This is precisely PocketBase's recommended pattern and is agent-trivial. Confidence: high.
- **v8go: eliminated.** rogchap/v8go is unmaintained; tommie/v8go is the active successor (https://github.com/tommie/v8go) — but it is cgo + per-platform V8 static libraries, which destroys "few dependencies + easy cross-compile" for no benefit at task-scale. Confidence: high on status, high on verdict.
- **QuickJS Go bindings:** the cgo binding (buke/quickjs-go) still carries an explicit "not ready for production" warning (https://github.com/buke/quickjs-go). New and notable: **modernc.org/quickjs** — a *pure-Go* QuickJS supporting **ES2023 including modules and async generators**, v0.23.0 published 2026-08-02, 14 GOOS/GOARCH combos, Go host functions via `RegisterFunc`: https://pkg.go.dev/modernc.org/quickjs. Pre-1.0, manual `Free()` memory management, bytecode format churn, no known large production users. It is the "watch closely" option: if it matures, it beats goja on language level (ESM, ES2023) while staying pure Go. Confidence: high on facts, medium on maturity judgment (no independent production reports found).

**Finding 3 — Option (b) WASM: strongest isolation, weakest guest DX for agent-written TS.**
- wazero v1.12.0 (2026-05-29) is the standard pure-Go, zero-dependency WASM runtime with a semver API promise; used by Trivy, dapr, Cilium-adjacent projects: https://wazero.io/, https://github.com/wazero/wazero. Hardening gap: no CPU bound (a hot loop hangs the calling goroutine — mitigate with context timeouts/`CloseWithExitCode`), memory limits must be configured: https://www.systemshardening.com/articles/wasm/wazero-hardening/. Confidence: high.
- Extism go-sdk (v1.7.1, 2025-03) is pure Go on wazero and is being adopted for **Helm 4's plugin system** — the marquee 2026 validation of this pattern: https://github.com/extism/go-sdk, https://helm.sh/community/hips/hip-0026/. Confidence: high.
- The TS→WASM path for user tasks is Extism js-pdk (v1.6.0, 2026-02-09) or Javy (now Bytecode Alliance, active Aug 2026): QuickJS-in-wizer, **ES2020 ceiling, CJS only, no fetch/timers/sockets, polyfill-land, WASI plumbing**: https://github.com/extism/js-pdk, https://github.com/bytecodealliance/javy, https://shopify.engineering/javascript-in-webassembly-for-shopify-functions. Honest verdict: for a platform whose tasks are TS written by agents, this stacks a compile step *and* a more restricted JS environment on top of everything option (a) already restricts, in exchange for a harder sandbox boundary. Justified only if the threat model treats task code as adversarial rather than merely buggy. Confidence: high.

**Finding 4 — Option (c) spawn-a-runtime: best language fidelity, breaks the deployment story the north star just added.**
- Precedent is strong: Windmill (Rust server) spawns Bun/Deno/Python per job — ~30ms cold start for Bun/Deno, dedicated warm workers for hot paths: https://www.windmill.dev/blog/launch-week-1/fastest-workflow-engine, https://github.com/windmill-labs/windmill. val.town runs per-task Deno subprocesses (prior report, verified then). Confidence: high.
- The problem is lodekit-specific: the *agent's laptop* has Node guaranteed, but the **self-hosted gateway engine** (VPS/NAS — the second writer in the sync pair) is exactly where "single binary, few deps" matters most, and this option reintroduces a managed Node/Bun install there. It also weakens the sandbox story back to OS-level controls (Deno's permission flags are real; Node's Permission Model is officially a seatbelt — per the verified prior report). Verdict: viable as a *degraded-mode* fallback ("tasks require a runtime on PATH"), wrong as the primary design. Confidence: high on facts, medium-high on verdict.

**Finding 5 — Option (d) no user server code: fails the product's flagship recipe.** Cron→webhook cannot target an SPA that isn't open; declarative pipelines break at the first `if` (the prior report's own analysis, which still holds). A "cron → HTTP-request-template → store response" primitive could cover a chunk of real usage, but "scheduled tasks with logic" is listed as a product differentiator, so (d) is a product retreat, not an architecture. Only take it as a deliberate scope decision. Confidence: high (product-logic, not empirics).

**RQ1 verdict:** goja (or sobek if ESM matters) with capability-bridged host functions, PocketBase-style pooled runtimes, agent-bundled single-file task code. WASM/Extism is the documented alternative if the sandbox requirement hardens. Spawn-Node as optional degraded mode at most.

Confidence: high on ecosystem facts; medium on the "build your own reconciliation" effort estimate.

### RQ4: The strangler path

**Finding 9 — "Go daemon first, engine later" is a credible and precedented strangler.**
- Step 1 (Go binary = supervisor + CLI + service install + reverse proxy to the existing Node engine) needs only stdlib `httputil.ReverseProxy` + **kardianos/service** (active — release July 2025, 1,431 importers, Windows/systemd/launchd/OpenRC): https://github.com/kardianos/service. This step delivers two north-star items (cross-platform daemon + CLI, Electron gone) *even if the engine rewrite never happens* — it is independently justified. Confidence: high.
- Direct prior art for proxy-first Node→Go: **Nhost's auth service** — Go process initially forwarding every request to the Node process, then absorbing endpoints one by one: https://nhost.io/blog/auth-to-go. Purpose-built tooling exists that logs parity between old and new servers and is explicitly designed so "a coding agent can drive the rewrite loop autonomously": https://github.com/vitorbaptista/strangler-fig-proxy. Confidence: high.
- Cross-language incremental ports at scale are the industry norm, not the exception: Turborepo ported 70k lines Go→Rust in 15 months with shim/sandwich strategies (https://vercel.com/blog/finishing-turborepos-migration-from-go-to-rust); and **Microsoft shipped TypeScript 7.0 GA on 2026-07-08 — the tsc compiler itself ported to Go, ~10x faster**, led by Hejlsberg, who rejected Rust because Go allowed a structurally identical port: https://visualstudiomagazine.com/articles/2026/06/22/typescript-7-0-rc-moves-microsofts-go-rewrite-into-the-mainline-compiler.aspx, https://www.infoworld.com/article/4100582/microsoft-steers-native-port-of-typescript-to-early-2026-release.html. Confidence: high.
- Absorption order that falls out naturally: (1) daemon/CLI/proxy → (2) static app-bundle serving + dashboard embed (trivial in Go, zero user code) → (3) stores + scoped API route-by-route behind the proxy (parity-checked) → (4) task runner (goja) → (5) sync protocol → (6) MCP subcommand on the official Go MCP SDK (v1.0, Google-maintained — per the contract axis, verified there). The Node engine shrinks to a task-only sidecar and then to nothing.

### RQ5: Learning/showcase axis

**Finding 10 — "Go single binary" is still the gold standard for this product class in 2026, and its showcase value strengthened this year.** The homelab/self-hosted consensus remains explicitly Go-flavored: Gitea/Forgejo praised as "single static binary, runs happily on 512MB" against GitLab's dozen services (https://danubedata.ro/blog/self-host-gitea-forgejo-github-alternative-2026, https://news.ycombinator.com/item?id=46097220, https://awesome-selfhosted.net/platforms/go.html); PocketBase at 60.4k stars is the leading single-binary BaaS; Syncthing/Tailscale/restic/NATS/Caddy remain the standing exemplars. Two 2026-fresh showcase datapoints: Microsoft picking Go for the TypeScript compiler (finding 9), and Helm 4 picking Go-native WASM (wazero/Extism) for plugins (finding 3). Counterweight for honesty: the TS world now has a credible single-binary answer too — Bun `--compile`, which is how Claude Code ships, and Bun is Anthropic-owned since Dec 2025 — so "single binary" alone no longer *forces* Go; the differentiators that remain Go-only are cross-compile breadth, memory footprint, no-runtime-to-manage, and the learning value itself. Confidence: high on sentiment; medium on how much weight "learning value" deserves (that's the person's call).

**Direct dependency count: ~6–8.** modernc.org/sqlite, dop251/goja (or grafana/sobek), kardianos/service, robfig/cron (optional), coder/websocket (only if WS needed — SSE may make it zero), official Go MCP SDK, golang.org/x/oauth2, fsnotify (if root-watching survives). No framework, no ORM, no NATS (unless chosen as sync transport), no esbuild, no cgo. Compare: the current engine's package.json plus the Electron manager toolchain.

**What the north star deleted from the 07-19 sketch:** embedded esbuild (agent builds apps), embedded NATS as a core component (single-process scale; SQLite tables suffice), the Tailwind-standalone-CLI wrinkle (agent-side now), and the entire SSR/worker hosting port.

## The two biggest risks

**Risk 1 — Multi-writer sync is a build-it-yourself protocol with zero ecosystem help.** cr-sqlite is dormant, sqlite-sync is license- and coordinator-bound, Marmot pivoted away from the SQLite-file model, and the commercial sync engines are client-sync products, not peer engines. The reconciliation protocol (versioning, clocks, tombstones, conflict policy per store type) is the hardest engineering in the plan, it lands on a young codebase in a language the project hasn't operated yet, and it has no comparator to crib from at this exact shape. Mitigation: lodekit owns the whole data API, so sync only has to merge SDK-shaped writes (kv entries, db-store rows, file metadata), not arbitrary SQL — a dramatically smaller problem than generic CRDT-SQLite. But it is genuinely novel work, and it is stack-independent: choosing Go neither causes nor cures it; it just shares the novelty budget with a rewrite.

**Risk 2 — The embedded-JS dialect gap between what agents write and what goja runs.** Agents reflexively emit ESM, `fetch`, `setTimeout`, npm imports, top-level await, ES2020+ syntax; goja offers ES5.1 + most-of-ES6 (async/await, generators, optional chaining: yes; ESM: no), no timers, no web APIs. PocketBase proves the model works at 60k-star scale, and its docs and forums equally prove the paper-cut stream is permanent. Every missing API becomes either a skill-level rule ("bundle to CJS, target es2017, use $gateway not fetch") or a new host bridge to build and maintain. Contained but chronic; the skill and the SDK typings must carry it forever. (Hedge to monitor: modernc.org/quickjs at ES2023-in-pure-Go could close most of this gap if it matures.)

## What is LOST vs the TS engine (honest ledger)

1. **The zod + Hono `hc` typed client and compile-time shared types across engine/SDK/dashboard/apps.** The single-language type flow dies. Replacement is OpenAPI-generated TS types from the Go engine — workable, and the 07-20 pass established OpenAPI is what agents want anyway, but it is codegen-at-a-boundary, not one type system; drift becomes possible where it currently isn't.
2. **The buildless dev loop.** `tsx` restart-on-save becomes compile-and-restart (Go compiles fast; still a loop change), and in-session engine hacking by the agent moves from "edit a .ts file under the running process" to a build step.
3. **~8,400 LOC of engine behavior re-derived in Go** — much smaller than the 07-19 report's 20k figure because SPA-only deletes the hosting/SSR/Vite subsystems from the port scope entirely, but settings resolution, gateway OAuth refresh, task catch-up semantics, event attribution etc. all still must be re-implemented and re-verified. The specs corpus describes a Node engine; ARCHITECTURE.md gets rewritten.
4. **The drizzle-in-TS schema contract** (if it survives SPA-only at all): either evaluated inside goja or replaced with SQL DDL/manifest — its own decision.
5. **npm ecosystem reach inside the engine** (OAuth quirks, one-off parsers). Go equivalents exist for the load-bearing cases; long-tail convenience is genuinely thinner.
6. **"The agent writes Go instead of TS" — mostly *not* a con in 2026.** Frontier agents are strong Go authors; Microsoft's own tsc-to-Go port normalized Go as the native language of JS-ecosystem tooling; and the platform is two-language *anyway* (apps/SDK/dashboard stay TS). The residual real cost is human: the owner reviews two languages, and engine↔SDK changes always touch both sides of a codegen boundary. The offsetting gain is the explicit north-star goal: the engine itself becomes the Go learning/showcase artifact, in the product class where Go is the community's default answer.

## Open questions

1. **Sync semantics before sync tech:** what does the product promise when laptop and gateway both write the same kv key / db row offline? LWW-per-field, LWW-per-row, or surfaced conflicts? This decision precedes any engine choice and is currently unspecified.
2. **goja vs sobek vs modernc.org/quickjs** for the task runtime: is experimental ESM (sobek) worth fork-tracking risk; is ES2023-pure-Go (modernc/quickjs) mature enough to bet on by the time the task-runner slice lands? Needs a 1-day spike each, re-checked at implementation time.
3. **Does "small server extensions" mean user-defined HTTP endpoints** (agent-written request handlers in the sandbox) or only tasks? Endpoints reopen per-request user code and change the goja pool sizing/threat model; the north star leaves this open.
4. **OpenAPI generation from Go**: which library (huma, swaggo, hand-maintained spec) preserves the "skill ships the contract verbatim" property — not researched this round.
5. **Sync transport**: plain HTTPS polling/push vs embedded NATS leaf nodes — only worth deciding after question 1; NATS re-enters only here, if at all.
6. **Strangler cut line**: does the Go daemon ship as its own release (replacing the Electron manager, engine still Node) before any engine porting begins? Finding 9 says yes is low-regret; the person should confirm this as the first committed slice.
7. **8,400-LOC figure**: the port-scope shrinkage argument assumes the hosting/Vite/worker subsystems are inside that count; worth a quick local audit of which files die under SPA-only before sizing the port.

# PER-CANDIDATE VERDICTS

## Node — verdict: YES, would bet 5 years on it (highest confidence among the JS runtimes)
Stewardship is strengthening, not decaying: annual every-release-is-LTS model from 27, native TS now Stable on the very line lodekit runs, node:sqlite at RC with an active stabilization push. The two things lodekit was waiting on (stable TS, stable sqlite) are respectively done and ~1 release away.
**First slice:** swap better-sqlite3 → node:sqlite behind the existing #141 seam, on Node 24 now (RC quality, sync `DatabaseSync` matches better-sqlite3's model; the gap is the `transaction()` helper — write a ~30-line shim in the seam). Optionally gate the default flip on Stable-2.0/26-LTS while keeping better-sqlite3 as the seam's fallback for one release. Do NOT make SEA the first slice (still experimental, CJS-single-file constraint conflicts with buildless).
**Buys:** kills the single worst brittleness (native ABI pin → bundled-Node version freedom, simpler prepare-bundle, no `pnpm rebuild` gotcha); shrinks dependency count; zero-cost reversible via the seam. **Forecloses:** nothing — it's also the prerequisite for any Bun path (F9: better-sqlite3 doesn't run on Bun anyway). Risk: RC-not-stable; mitigated by the seam and by DatabaseSync's small surface. The Aug 4 blocker list (F2) suggests stabilization is being actively driven; watch whether it lands by 26 LTS (Oct 2026).

## Bun — verdict: NOT today for a 5-year bet
The technology is attractive (native sqlite, single-binary compile, speed), but every stewardship indicator points the wrong way right now: 3-month release stall, 1.4 rewrite merged-but-untagged, no LTS channel and documented versioning indiscipline, measurable team attrition, 3,828 open issues + 4,409 open PRs with an AI-generated PR queue doubling in 18 days. Anthropic's backing guarantees survival but re-aims the roadmap at Claude Code's needs, not at "boring runtime for third-party products." The specific kill-question (#29124) is still open with an unmerged fix.
**First slice:** run the already-scoped #142 spike anyway — it is cheap and its information value is the point — but time-box it and treat the expected outcome as "not yet": test (a) whether worker specifiers can be constrained to the plain-relative form that does work in compiled binaries (F8), (b) node:sqlite-polyfill fidelity vs the seam's contract, (c) worker_threads (not just Web Worker) behavior compiled.
**Buys:** resolves the #153 fork with evidence; if it unexpectedly passes, unlocks single-binary engine + built-in sqlite in one move. **Forecloses:** nothing if run as a spike; committing (not spiking) would foreclose the stability story until Bun grows an LTS. Re-evaluate after a stable 1.4 tag ships and holds for 2–3 patch releases.

## Deno — verdict: technically yes, organizationally no (medium-low for 5 years)
The runtime itself is in good shape (steady 2.9.x cadence, LTS channel active to Jan 2027, Node 26 compat, `deno compile` mature-ish) and its permission model is the only off-the-shelf answer to lodekit's "no sandbox for app code" gap. But the company carries real risk: no funding since 2022, March 2026 layoffs, revenue pivot to Deploy/Sandbox, and a demonstrated willingness to hard-EOL products (Deploy Classic, Jul 20, 2026). A 5-year bet on `deno compile` + permissions is a bet on Deno Land Inc.'s continuity or on the (plausible but unproven) community's ability to carry the runtime.
**First slice:** a compile-the-engine spike mirroring #142: engine + worker-hosted local app code under `deno compile --include`, measuring (a) worker + local dynamic import behavior in the binary (the open #33218 covers only remote fetches — local behavior needs empirical testing), (b) whether Deno's permission flags can express per-app sandboxing, which neither Node nor Bun offers.
**Buys:** data on the only candidate that addresses the sandbox gap natively. **Forecloses:** if adopted, ties lodekit to npm-compat shims for its ecosystem and to a company in a fragile phase; also the largest migration surface of the three JS options (permissions model leaks into everything).

## Go — verdict: YES on stewardship (the strongest of the four); the right question is scope, and the manager-first slice scopes it correctly
Go's stability profile is a different league: 6-month cadence hit for a decade, Go 1 compat promise, boring security patch trains, true static cross-compiled binaries for all 3 OSes. The cost is a full rewrite of anything moved to it — which is why the strangler slice matters.
**First slice:** rewrite the manager/supervisor as a Go daemon+CLI (+ tray) that supervises the Node engine child, replacing Electron while the engine stays untouched. This exact shape is proven at scale: Ollama's app is literally "Go process: tray + webview + supervises server subprocess" (F14a), and Tailscale's daemon+CLI-over-local-socket is the canonical 3-OS Go daemon pattern (F14b). Concrete stack: kardianos/service (launchd/systemd/Windows SCM), fyne.io/systray or energye/systray for the tray (cgo on macOS; Tailscale vendors its own fork — plan for that possibility), local HTTP over unix socket/named pipe between CLI/tray and daemon, `exec.Command` supervision of the bundled Node engine with restart/backoff (the current manager's supervisor semantics port directly). 1–2 weeks is realistic for daemon+CLI+launchd on macOS with tray as a stretch; 3-OS service integration is the follow-on slice, not this one.
**Buys:** kills the Electron weight and the macOS-only manager in one move; delivers the north star's daemon+CLI shape immediately; creates the natural future home for sync/multi-writer coordination code; maximal learning value; engine risk = zero. **Forecloses:** nothing about the engine runtime — it is explicitly orthogonal to the #153 fork; the only lock-in is maintaining a second language in the repo. Known frictions: macOS signing/notarization of the Go binary (already a solved problem for the Electron bundle), cgo for the tray icon on macOS, and losing whatever Electron UI surface the manager has (mitigate Ollama-style: webview or `open http://localhost:7777/_dashboard/`).
